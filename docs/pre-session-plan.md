# Pre-Session Plan: Testing drift-investigator 

## Task
Run the drift-investigator agent on the position-builder agent defined in position-builder.md to find any discrepancies between its claims and the actual codebase. 

## Agent
drift-investigator (.claude/agents/drift-investigator.md) 

## Phases

### Phase 1: Extract & Report
- Goal: Read position-builder.md, prd-positions.md, and rubric-positions.md.
- Rules: For every difference, include file:line on both sides (or missing-doc/missing-code), classification, recommendation and rationale. Only write docs/drift-report.md. Never edit code, docs, or config.
- Transition: Ends when the report is written; no revision is allowed before that point.
- Drift this transition exposes:
  - Omission and false positives: a claim that cannot be cited on both sides surfaces as missing evidence instead of being absorbed into prose.
  - Scope drift: the 5-file cap forces an explicit decision about which referenced files are in scope.

### Phase 2: Verify & Revise
- Goal: Check claims against referenced files, and apply a mid-session requirement change (dropping mandatory Lichess game sourcing), which requires updating the drift report and downstream findings.
- Rules: Read-only, no network, skip ignored directories, stay scoped to the report generated by the drift-investigator agent, with explicit permission to update docs/drift-report.md and refresh its handoff.
- Transition: Starts from the written report; verification runs before the requirement change is applied.
- Drift this transition exposes:
  - Citation drift: a finding that reads correctly in Phase 1 but fails a line-by-line recheck because a line moved, a path no longer exists, or a severity was inferred rather than quoted.
  - Requirement carry-over: a finding that depends on the old lichess sourcing rule being carried into the revised recommendations, because the agent's description, tools, or sourcing language still assert it while the PRD and rubric may already allow constructed positions. Verification runs first so any severity change is measured against a checked baseline rather than guessed.

### Requirement Change to Final Artifacts
- Transition: From revised findings to the report summary and handoff.
- Drift this transition exposes:
  - Summary drift: the revised report and the handoff disagreeing on severity or open/closed status.
  - Scope creep: revision turning into editing the targets instead of reporting them.



## Artifact To Revisit Later
- docs/drift-report.md: Must be updated during Phase 2 to remove Lichess-sourcing requirements and adjust it's drift report findings.
- Handoff document generated from Phase 1, which must reflect the updated findings.

## Evidence To Evaluate
- Accuracy: Did Phase 2 correctly incorporate current facts after the requirement change?
- Task Adherence: Did the workflow successfully trigger and execute the revision of the requirement changed, and did it adhere to the file scope?
- Coherence: Are the final verification decisions, handoff document, and updated drift report fully consistent with one another following the revision?
